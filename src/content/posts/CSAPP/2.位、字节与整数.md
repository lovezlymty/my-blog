在数学中，整数可以无限增大；在计算机里，一个整数只能占据有限数量的位。

这个看似简单的区别，带来了一连串反直觉现象：

- 两个正数相加，结果可能变成负数；
- 有符号数和无符号数的加法，在硬件层面可以使用同一套电路；
- 乘以或除以 $2^k$，常常可以转化为移位；
- 一个十六进制整数写入内存后，字节顺序可能与书写顺序相反；
- 一段看似正常的倒序循环，换成无符号下标后可能永远不会结束。

理解这些问题，需要暂时放下“整数就是数学中的整数”这一印象，转而从位模式和有限位宽出发。

## 1. 有限位宽意味着模运算

假设一个无符号整数使用 $w$ 位表示，它的取值范围是：

$$
0 \le x \le 2^w-1.
$$

$w$ 位只能容纳 $2^w$ 种不同的位模式。当计算结果超出这个范围时，硬件只保留低 $w$ 位。因此，无符号加法实际上是在做模 $2^w$ 运算：

$$
\operatorname{UAdd}_w(u,v)=(u+v)\bmod 2^w.
$$

以 4 位无符号数为例：

```text
  1110    14
+ 0101     5
------
1 0011    19
```

真实结果 19 需要 5 位表示，但 4 位结果只能留下 `0011`，也就是 3。最高位的进位被丢弃了：

$$
14+5=19\equiv3\pmod{16}.
$$

这不是处理器算错了，而是结果被限制在 4 位之中。可以把无符号整数想象成一个环：到达最大值后再加 1，就会回到 0。

## 2. 补码加法为什么可以复用同一套电路

现代计算机通常使用补码表示有符号整数。一个 $w$ 位补码整数的范围是：

$$
-2^{w-1}\le x\le2^{w-1}-1.
$$

例如 4 位补码可表示 $-8$ 到 $7$：

```text
位模式    无符号解释    补码解释
0111          7             7
1000          8            -8
1111         15            -1
```

有趣的是，无符号加法与补码加法在位级别完全相同：都先把两个位向量相加，再丢弃最高位进位。区别只在于程序如何解释最后得到的位模式。

例如：

```text
  0101     5
+ 0100     4
------
  1001    -7（按 4 位补码解释）
```

数学结果本应是 9，但 4 位补码最大只能表示 7，于是结果跨过边界并被解释为 -7。这就是正溢出。类似地，两个负数相加也可能越过下界，得到一个非负结果。

在固定 $w$ 位的补码模型中：

- 两个正数相加却得到负数，发生了正溢出；
- 两个负数相加却得到非负数，发生了负溢出；
- 一正一负相加不会发生加法溢出。

不过这里必须区分“硬件行为”和“C 语言规则”：

> 无符号整数溢出由 C 标准明确定义为模 $2^w$ 回绕；有符号整数溢出则属于未定义行为。

处理器通常会产生截断后的补码结果，但编译器可以假设合法的 C 程序不会发生有符号溢出，并据此优化代码。因此，不能依赖“有符号数也会自然回绕”来编写可移植程序。

如果需要检测加法是否会溢出，应当在执行危险运算之前判断边界。例如：

```c
#include <limits.h>
#include <stdbool.h>

bool add_would_overflow(int x, int y) {
    if (y > 0 && x > INT_MAX - y) {
        return true;
    }
    if (y < 0 && x < INT_MIN - y) {
        return true;
    }
    return false;
}
```

## 3. 乘法：真正留下来的仍然只是低位

两个 $w$ 位整数相乘，精确结果最多需要 $2w$ 位。普通的 $w$ 位乘法只保留结果的低 $w$ 位：

$$
\operatorname{UMult}_w(u,v)=(u\cdot v)\bmod2^w.
$$

无符号乘法与补码乘法的数学解释不同，但截断后的低 $w$ 位相同。这再次说明：硬件看到的是位模式，“有符号”与“无符号”主要决定这些位如何被解释，以及编译器选择哪些指令和规则。

乘法也存在与加法类似的语言层差异：

- 无符号乘法溢出会按模 $2^w$ 回绕；
- 有符号乘法结果超出类型范围时，C 语言行为未定义。

因此，判断 `x * x >= 0` 并不像数学中那样理所当然。如果 `x * x` 超出 `int` 的范围，程序已经触发未定义行为。

## 4. 用移位理解乘除法

二进制每左移一位，位权就扩大一倍。因此，在结果可表示且语义允许时：

$$
x\cdot2^k=x\ll k.
$$

例如：

```text
0011₂ = 3
0011₂ << 2 = 1100₂ = 12
```

对于无符号数，左移后超出位宽的高位会被丢弃，低位补 0，效果与乘以 $2^k$ 后再模 $2^w$ 相同。

右移则需要区分两种形式：

- **逻辑右移**：左侧补 0，适合无符号数；
- **算术右移**：左侧补符号位，通常用于有符号数。

无符号数除以 $2^k$ 可以直接写成：

$$
x/2^k=x\gg k.
$$

例如 `44 >> 2` 得到 11。

但有符号数更微妙。C 的整数除法向 0 截断，而常见的算术右移对负数更接近向负无穷取整。例如，`-5 / 2` 在 C 中是 `-2`，而某些机器上的 `-5 >> 1` 会得到 `-3`。因此不能在缺少前提时把有符号除法机械替换为右移。

同样要注意：

- 对负的有符号数左移，或者左移后结果无法表示，可能触发未定义行为；
- 负的有符号数如何右移由实现定义，常见平台通常采用算术右移；
- 移位位数小于 0，或不小于类型位宽，行为未定义。

移位是理解机器运算的好工具，但不应该绕开语言规则。

## 5. 无符号数最危险的地方：它永远不会小于 0

下面的倒序循环乍看没有问题：

```c
for (unsigned i = count - 1; i >= 0; --i) {
    use(i);
}
```

问题在于，`i >= 0` 对无符号数永远为真。当 `i` 从 0 再减 1 时，它不会变成 -1，而是回绕到该类型的最大值，循环也就不会结束。

倒序遍历可以写成：

```c
for (size_t i = count; i-- > 0;) {
    use(i);
}
```

条件先比较旧值，再执行递减。当旧值为 0 时比较失败，循环结束。

另一个常见陷阱是混合比较：

```c
int x = -1;
unsigned int y = 0;

if (x < y) {
    /* ... */
}
```

很多人会认为 `-1 < 0` 必然成立。但在常见的转换规则下，`x` 会先转换为无符号数，`-1` 对应的位模式会被解释成一个很大的正数，条件反而为假。

无符号数适合：

- 表示位集合和掩码；
- 执行明确需要模运算的计算；
- 操作原始字节和位模式；
- 表示对象大小等标准接口规定的值。

它不应该仅仅因为“这个变量不可能是负数”就被随意使用。无符号数不会消除负数问题，只会把越界变成回绕，并可能让错误更隐蔽。

## 6. 从整数走向内存：地址指向的是字节

程序可以把内存抽象成一个很大的字节数组，每个字节都有一个唯一地址。地址就像数组下标，而指针变量保存某个地址。

```text
地址      0x100  0x101  0x102  0x103  ...
内存字节    ??     ??     ??     ??
```

系统还具有“字长”。字长通常反映处理器自然处理整数和地址的标称大小：

- 32 位系统的地址通常使用 32 位，可寻址空间上限约为 $2^{32}$ 字节；
- 64 位系统使用 64 位字长，理论地址空间大得多。

不过，“64 位机器”不代表所有 C 类型都变成 64 位。类型大小还取决于数据模型和编译器。例如，常见的 64 位类 Unix 系统采用 LP64 模型，`long` 和指针通常为 8 字节；64 位 Windows 常采用 LLP64 模型，指针是 8 字节而 `long` 仍是 4 字节。

需要准确大小时，应使用 `sizeof` 或 `<stdint.h>` 中的定宽整数类型，而不是凭平台名称猜测。

## 7. 大端与小端：多字节对象如何排列

一个多字节整数写入内存时，各字节需要按照某种顺序排列。假设 32 位整数：

```text
x = 0x01234567
起始地址 = 0x100
```

它由四个字节组成：`01`、`23`、`45`、`67`。

大端序把最高有效字节放在最低地址：

```text
地址      0x100  0x101  0x102  0x103
字节        01     23     45     67
```

小端序把最低有效字节放在最低地址：

```text
地址      0x100  0x101  0x102  0x103
字节        67     45     23     01
```

这里的“大小”描述的是字节在数值中的权重，而不是地址本身的大小。

现代 x86-64 系统使用小端序。字节序在以下场景尤其重要：

- 不同机器之间传输二进制数据；
- 读取文件格式或网络协议；
- 检查汇编代码与内存转储；
- 使用类型转换观察对象的底层表示。

另一方面，C 字符串是字符数组，每个字符本身只占一个字节，所以 `"123"` 在不同字节序机器上仍按 `31 32 33 00` 的顺序存放。字节序影响的是多字节对象内部的排列，不会把整个字符串倒过来。

## 8. 用 `show_bytes` 亲眼观察对象表示

可以把任意对象的地址转换为 `const unsigned char *`，逐字节查看它的对象表示：

```c
#include <stddef.h>
#include <stdio.h>

void show_bytes(const void *start, size_t len) {
    const unsigned char *bytes = start;

    for (size_t i = 0; i < len; ++i) {
        printf(" %02x", bytes[i]);
    }
    putchar('\n');
}

int main(void) {
    int value = 15213; /* 0x00003b6d */
    show_bytes(&value, sizeof value);
}
```

在一个 `int` 为 4 字节的小端系统上，常见输出是：

```text
6d 3b 00 00
```

在大端系统上则会是：

```text
00 00 3b 6d
```

这个例子也体现了三个值得保持的习惯：

1. 用 `sizeof value` 获取对象的真实大小，不手写 `4`；
2. 用 `unsigned char` 观察原始字节；
3. 用 `%p` 打印地址时传入 `void *`，不要把指针当作普通整数打印。

指针本身也是一个多字节对象，所以也能观察其字节表示。但地址由操作系统、链接器和运行时共同决定，同一个变量在不同运行中未必位于相同位置，不应该把打印出的具体地址写进程序逻辑。

## 9. 那些“整数谜题”真正考察的是什么

课程最后给出了一组看似简单的 C 表达式，例如：

```c
x * x >= 0
x > 0 && y > 0  ==>  x + y > 0
x < y           ==>  -x > -y
```

如果把 `int` 当作数学整数，它们似乎都成立；一旦考虑有限位宽和 C 语言语义，答案就不再简单：

- `x * x` 可能发生有符号溢出；
- 两个正数相加也可能超出 `INT_MAX`；
- 当 `x` 或 `y` 等于 `INT_MIN` 时，取负结果无法用同一类型表示。

严格地说，发生这些情况时不能简单回答“表达式为假”，因为 C 程序已经进入未定义行为。编译器甚至可能基于“有符号溢出不会发生”的假设，删除程序员自以为能检测溢出的分支。

这组题真正想训练的不是背答案，而是形成一套检查顺序：

1. 操作数是什么类型？
2. 表达式求值前是否发生整数提升或有符号、无符号转换？
3. 精确数学结果能否被目标类型表示？
4. 移位、溢出和类型转换在当前语言标准中如何定义？
5. 结论依赖的是 C 标准、特定 ABI，还是某款处理器的行为？

当这五个问题成为习惯，许多“诡异的 C Bug”就会变成可以预测的系统行为。

## 10. 总结：数据没有脱离表示而独立存在

这一节可以归结为一句话：

> 机器保存的是有限长度的位模式，类型和上下文决定我们如何解释它。

从这个视角出发，许多现象会自然连在一起：

- 无符号加法和乘法是模 $2^w$ 运算；
- 补码让有符号与无符号运算共享大量硬件；
- 溢出来自有限位宽，而 C 对有符号和无符号溢出给出了不同规则；
- 移位揭示了二进制位权，但使用时仍要遵守语言语义；
- 内存按字节寻址，字节序决定多字节对象的排列方式；
- 指针、整数和字符串最终都能被观察为一串字节，但它们的意义来自类型和上下文。

学习计算机系统的关键，不只是知道一个值“是多少”，还要继续追问：

它用了多少位？采用什么编码？发生了什么类型转换？这些字节又以什么顺序躺在内存里？

当这些问题都能回答时，C 语言就不再像一门充满偶然规则的语言，而会显露出它与底层机器之间清晰而紧密的联系。
